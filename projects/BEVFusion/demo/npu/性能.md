**一览表关键结论**：

1. **前三大耗时**：img_backbone 36%（~166ms，Swin-T 12 块；2026-09-30 优化后）> view_transform 整体 25%（~116ms，含 LiDAR 投影 ~75）> sparse_encoder 25%（~118ms）
2. **bev_pool 已是次要项**：v1 原子加 kernel 全链 ~23ms（op 19.7 + prep/permute），
   不再是最优优化靶——LiDAR 投影（~75ms）与 sparse_encoder（~118ms）才是剩余大头
3. **get_geometry CPU 补丁已基本免费**：numpy 副本预计算后仅 ~5ms H2D，D2H 排干已消除
   （精度/性能三方 A/B 见 §1.3）
4. **voxelize AICPU Sort 已消除**：AscendC 化后整段 25.3ms（旧 torch 路径 72ms，其中
   Sort AICPU ~39ms）
5. **数据搬运/布局风暴仍在**：Swin/BEV/spconv 链路的 gather/scatter/transpose 小算子风暴
   是 310P 主战场（详见 §5 profiling 复盘）

### 1.1.1 unum_ops 原子加 bev_pool kernel（2026-09-20 重写）

**算法**（对标 mx_driving 的算法级优势，消除排序/收集/区间构建流水线）：
- host 预乘元素偏移 ranks `off = (((b*D+z)*H+x)*W+y)*C`（int32 精确，实测 321M 逐位正确）
- kernel 逐点：标量读 rank → OOB（`off ≥ gridTotal*C`）零写流量跳过 → `SetAtomicAdd<float>` +
  80-float `DataCopy` 直写 BEV cell（MTE3 原子累加）→ `SetAtomicNone`（mx 同款逐点切换）
- tile 间 `PipeBarrier<PIPE_ALL>` 串行纪律（沿用旧 segment-sum kernel 验证过的 MTE2→标量门控；
  首版整块原子提升 + ping-pong 事件会间歇性挂死 310P，transposed kernel 背锅，已废弃）
- **NPU 大 int32 坑（重要）**：≥2^28 的 int32 过 `torch.where`/比较算子会被内部 FP32 量化
  （268435455→268435456，`269567999 < 269568000` 判 False）。OOB 修正改用小值域判定：
  坐标逐维 `<W/<H/<D` 生成 mask + 小值 where 把越界点 batch 列置为 B（rank 自然 ≥ 上界被
  kernel 跳过），全程不触碰大值 where/比较

**实测（1.84M 点，B=1, D=41, H=W=180, C=80）**：

| 指标 | unum_ops 原子版 | mx_driving v3 | QuickCumsum |
|---|---|---|---|
| 全链总耗时 | **31.4ms** | 34.4ms | 399ms |
| ranks 预处理 | 2.5ms | 4.0ms | — |
| op 调用（zeros+kernel） | **19.7ms** | 24.4ms | — |
| 输出 permute | 6.4ms | 9.0ms | — |
| 对 CPU 参考精度 max_abs | **4.8e-7** | 1.95e-5 | ~1e-6 |
| OOB 点处理 | kernel 内零写流量跳过 | 需 host sanitize（乘 0 仍写 320B/点） | kept 过滤 |

- kernel 单体 ~17.2ms vs mx 21.9ms（**快 21%**，主因 OOB 点零写流量——30% 点不产生 MTE3 负载）
- 稳定性：15/15 独立进程（kernel only / kernel+transpose / 完整 wrapper）
- 多 batch 正确性：B=1/2/3、gridTotalC 高至 321M（跨 2^28 边界）全对（修复大 int32 where 量化后）

#### O3：消除 NonZero/UniqueWithCountsExt2/Index 热点

- frustum gather 链：`x[kept]` + `geom_feats[kept]`（105ms + 63ms Index + NonZero 17ms）
  → 改为 `x * kept.mask` + coords clamp（零特征点贡献 0，语义等价）。见 depth_lss.py
- `_downsample_coords` 的 list-comprehension `[lo[keep] for lo in los]`（每次 keep 各
  NonZero 一次）→ 单次 `torch.nonzero(keep)` + `index_select` ×N（conv.py）
- voxelization 的布尔掩码 gathers（valid / max_voxels / max_points 分支）→ 单次
  nonzero + index_select（voxelize.py）
- SparseConv3d 输出去重 `torch.unique(out_i, dim=0)`（UniqueWithCountsExt2 AICPU
  12.6ms×2）→ float64 key 编码 + `torch.argsort`（AiCore）+ 相邻比较去重（conv.py build()）
- **效果：E2E 0.9-1.2s → 0.7s（3/3 轮一致），48 dets / 0.819478 与基线逐检测
  diff ≤1e-4**（唯一差异是同一 pedestrian 的 1e-4 score 重排噪声）

#### O5：get_geometry numpy 副本预计算（`patch_get_geometry_overlap`）

- **勘误**：早期版本曾写"去掉 CPU 补丁 E2E 无加速（0.7s==0.7s）"——那是 0.1s 精度计时的
  误判（0.66 和 0.70 都打印 0.7s）。demo.py 计时已升级到 ms 级，重测真相：纯 CPU 补丁
  净成本 **~37ms/帧**（694 vs 664ms 三方 A/B）
- 机制：补丁的 `.cpu()` D2H 在主流上排在 Swin 之后，必须等 Swin 排干才开始 CPU 计算，
  期间设备空转 ~44ms
- v1 失败教训（矩阵提前 D2H 到 extract_img_feat 入口 → 850-890ms 更慢）：主流上任何
  D2H 都要等全部先前任务排干；提前 D2H 只让主机在 Swin **入队前**就被阻塞，设备空转入队期。
  **结论：主流 D2H 无法与设备重叠，唯一出路是让数据根本不上 NPU 就拿到 CPU 副本**
- v2 实现（npu_patches.py `patch_get_geometry_overlap`）：标定矩阵的诞生地在 `extract_feat`
  ——由 metas 的 numpy 数组经 `imgs.new_tensor` 构建。hook `extract_feat` 在构建前留存
  numpy 副本（微秒级、零 D2H）；`extract_img_feat` 入队 backbone/neck 后用 CPU 副本
  预计算几何；`get_geometry` 命中 stash 只做 H2D——省掉纯补丁的 D2H 排干等待（~37ms/帧）
- 数值：几何输出与纯 CPU 补丁**逐位一致**（含 `.contiguous()` 布局统一，消除了 v1 观察到的
  1.5e-5 系统性差异）；48 dets / 0.819478；npu_test.py Runner 路径同样命中 stash（已 smoke 验证）
- **附赠发现：下游 NPU 管线存在 ±1e-4 运行间 score 噪声**（几何逐位相同的两次纯补丁运行，
  max score 0.819478 vs 0.819399）——今后精度对比的噪声地板

#### O11：Swin ShiftWindowMSA shift 路径优化（2026-09-30，bit-exact）

- **背景**：Swin-T（swin_tiny checkpoint，embed 96 / depths [2,2,6,2] / 窗 7×7 / 全 stage
  head_dim=32）串行探针成本地图（两端 sync 探针 + 独立微基准交叉验证，~192ms）：
  attention core 算子链 75.7（39%）、FFN 50.9（GEMM 44 健康 + GELU ~10 + 残差 ~2）、
  qkv+proj GEMM 33.9、partition/roll/mask 23.4、LN+残差 ~11。完整调查记录见 §3.3.7
- **两项优化**（npu_patches.py `patch_swin_shift_optimizations`，`NPU_PATCH_SWIN_SHIFT=0` 可关）：
  1. **attn mask 全局缓存**：mmdet 每个 shift 块每帧重算 mask 构建链（img_mask 填充 +
     window_partition + masked_fill，~15 个小算子，实测 1.48ms×6 块）。mask 是
     (H_pad, W_pad, window, shift) 的纯形状函数 → 全局 dict 缓存，首帧后零开销
  2. **pad/roll 四切片融合**：mmdet 的 `F.pad(右/下) + roll(−s,−s)`（2 次全帧拷贝，实测
     0.67+2.31ms）在 pad≥shift 时代数等价于 zeros+4 切片装配（主块+列/行/角卷绕，1 次拷贝
     ~1.9ms）；反向 `roll(+s) + slice + contiguous()`（2 次拷贝，2.31+~1ms）等价于 4 切片
     装配（1 次拷贝）。roll 会把 orig 头部行/列卷绕到帧尾——这正是 shift mask 存在的原因，
     融合版必须完整保留 4 个卷绕块（首版漏了 wrap 语义 bit-equal 即 False）
- **验证**：8/8 配置（4 stage 形状 × shift 0/3）原始 vs 补丁 forward **逐位相等**
  （max_abs 0.0e+00，融合路径与 fallback 路径都过）；mask 缓存 vs 原始构建逐位相等；
  demo E2E 48 dets / 0.819478 / 逐类一致
- **收益**：Swin 串行探针 partition/roll 桶 23.4→12.4ms；E2E 20 轮交错 A/B median
  486→477ms（-9ms）。探针 -11ms 与 E2E -9ms 的差值来自管线内 host-bound 空转
  （mask 链的小算子部分藏在设备等入队的空隙里，删除后 wall time 收益略小于设备时间收益）
- **守卫**：融合路径仅在 `shift>0 ∧ pad_b≥s ∧ pad_r≥s ∧ H>s ∧ W>s` 时启用（本模型四
  stage pad 为 6/6、3/3、5/5、6/6，shift=3，均满足）；否则严格回退原始路径

#### O12：LiDAR 投影 trash 列向量化（2026-09-30，bit-exact，E2E -31ms）

原始 `BaseDepthTransform.forward` 的 b×6 相机循环是 NPU 反模式组合，op_summary 实测
（独立段 44.7ms，设备 41.7ms）：

| 项 | 耗时 | 处置 |
|---|---|---|
| NonZero（AICPU）×12 | 11.4ms | ✅ 消（trash 路由免布尔索引） |
| Index gather ×13 | 6.4ms | ✅ 消（同上） |
| 数学链 matmul ×3 | 10.7ms | ❌ 不动（bit-exact 契约：fp16 cube 归约序不可变） |
| mask 比较 Ge/Lt ×24 | 3.5ms | 保留（trash 方案仍需 valid 判定） |
| IndexPut scatter ×6 | 2.3ms | 变全量（250K/相机，实测仍便宜） |
| 6 次 `.any()` 同步 + CPU zeros + 4.3MB H2D | — | ✅ 消 |

**设计**：depth 直接在设备上分配 (B, C, 1, H, W+1)，无效点（越界/NaN 坐标经 mask 比较
自然落选）统一路由到 (0, W) trash 格，逐相机**全量赋值** `depth[b,c].view(-1)[flat]=dd`
——保持每相机内点序，重复单元 last-wins 与原始逐位一致；末尾 narrow[..., :W] 丢弃
trash 列。独立段 44.7→24.8ms；view_transform 管线段 116.2→95.7ms；E2E 25 轮进程级
交错 A/B median 481→**450ms（-31ms）**——比段级多出的 ~10ms 来自去同步后 host 跑得
更 ahead（串行探针口径看不到的排队收益）。

**与历史两次失败的区别**（§3.3.2/§3.3.6，勿混淆）：
- 3.3.2（batched scatter）只批化了 scatter——但 scatter 本来不是热点（2.4ms），真正的
  布尔 gather 21.8ms 原封未动，且 `index_put_` 走 AICPU 反慢 26%。O12 消的是 gather
  （NonZero+Index），赋值用逐相机 advanced-index 赋值（非 index_put_），实测 2.3ms 档
- 3.3.6（整段 CPU 化）撞 CPU 串行窗口（与 geometry 预计算串行超 Swin 窗）。O12 全程
  留在 NPU 上，无 CPU 负载新增

**精度验证**：depth 图与原版 bit-exact（torch.equal）；E2E 逐类计数与历史基线完全一致
（barrier 19 / car 3 / moto 1 / ped 20 / cone 3 / truck 2 = 48）；跨模式检测明细 diff
（22 行）小于模式内轮间噪声（24-26 行）——落在已知原子加重排噪声带内。
env `NPU_PATCH_LIDAR_PROJ=0` 可关；非 NPU 设备运行时自动回退原始实现。

### 3.3 2026-09-22 定向优化尝试（全部证伪/回退，避免重复工作）

#### 3.3.1 view_transform 真实分布（forward 探针，device-event）

"77ms LiDAR 投影归因"与"126−71=55ms 黑洞"均为**假象**（此前是残差相减的推算）。真实分布：

| 段 | 实测 | 说明 |
|---|---|---|

| get_geometry / downsample | 4.3 / 4.1ms | |

#### 3.3.2 尝试一：LiDAR 投影 batched scatter（2026-09-22 上午，已回退）

- 方案：6 相机循环 scatter 改为一次性 `index_put_`（flat index 全局写），CPU 验证逐位等价
- **实测证伪**：NPU 上 `index_put_` 走 AICPU 逐点累加，**11.94ms vs 原 for 循环 9.49ms（慢 26%）**；
  且真实 forward 里 scatter 仅 2.4ms（投影大头是布尔 gather 21.8ms，不是 scatter）
- 教训：NPU 的 `index_put_` 比直接张量赋值慢；"77ms 残差归因"不可信
- **后续（2026-09-30）**：✅ 该问题已由 O12 解决——trash 列路由消掉布尔 gather 本体
  （而非批化 scatter），逐相机 advanced-index 赋值避开 index_put_ AICPU，E2E -31ms

#### 3.3.3 尝试二：bev_pool prep CPU 化（2026-09-22 中午，已回退）

- 方案：量化/kept/ranks 全搬 CPU（复用 geom stash），NPU 只收 int64 coords / int32 ranks
- **实测证伪**：CPU 上 1.99M 点 prep **150-175ms，比 NPU 上 28.2ms 慢 6x**；且
  `_compute_geometry_cpu` ~180ms 已近 Swin 177ms 并行窗口上限，prep 加入后 CPU 串行块超窗
  成新瓶颈，full extract_feat 682-716ms（+150-180ms）
- 教训：**NPU 的 int 张量操作比 CPU 快一个数量级**，CPU 化量化类 prep 是方向性错误；
  也不要往 AscendC kernel 逐点循环加标量计算（kernel 标量发射受限，见 AGENTS.md）

#### 3.3.4 尝试三：bev_pool kernel 内部优化（2026-09-22，unum_ops 分支已回退）

- 目标：消除 feats gather 15ms + permute 6.4ms
- **实测证伪**：
  - gather 是**过时前提**（wrapper 的 sort+index_select 已在 56b982a 删除，host 无 gather）
  - permute 本 demo 帧（D=1，网格 41.5MB）实测仅 **1.0-1.8ms**；消除必回归（直写
    (B,C,D,H,W) 需每点 C=80 次散落原子写，MTE3 流量 ×80）
  - 唯一可消项 host ranks prep 8.5ms 移入 kernel 后 kernel 13.2→23.4ms（+10.2ms）净亏
- **顺带确认 baseline max score 非确定**：0.819399/0.819399/0.819478 随机翻转（跨核原子
  竞争），"逐位一致"验收口径应改为 48 dets + max ∈ {0.819399, 0.819478}

#### 3.3.5 尝试四：SWA 融合算子微基准（2026-09-22，/tmp/opencode/swa_bench）

- 目标：验证融合 window_partition + qk+bias+softmax+@v 的收益（决策门 >80ms 建 / <40ms 弃）
- 真实形状：stage0 64×176（非 112×112），1560 窗口 × 6 图，C=96，3 head

#### 3.3.6 尝试五：LiDAR 投影整体 CPU 化（2026-09-24，已回退）

- 目标：LiDAR 投影 45.9ms（gather 21.8 + matmul 16.8 + mask 4.8 + scatter 2.4）整体移 CPU，
  复用 patch_get_geometry_overlap 的 stash 机制（CPU 侧算 depth，view_transform 只 H2D）
- 与 3.3.2（scatter 批化）不同：这是整段投影 CPU 化（45.9ms 全消，CPU 预估 ~7ms）
- CPU bit-exact 验证通过：非重复像素 4165/4165 全部 bit-exact，差异 100% 集中在
  重复索引区域（PyTorch `depth[rows,cols]=d` 对重复索引是 undefined 语义，NPU 原版同样不确定）
- demo 验证：48 dets / car 3 + truck 2 + barrier 19 + motorcycle 1 + ped 20 + cone 3——与 baseline 100% 一致
- **严格同进程 A/B（device-event，交替 flag）证伪**：PATCHED 608.7ms vs ORIG 601.4ms，
  **净亏 7.3ms**。原因：`_compute_depth_proj_cpu` 与 `_compute_geometry_cpu` 在 extract 预计算块
  (b) 内**串行**，host 负载下 CPU 耗时膨胀超 Swin 177ms 并行窗口，成为新瓶颈
- **结论与尝试二一致**：CPU 串行路径在 NPU 上无优势——NPU 的 scatter/matmul 虽显式在
  设备端，但 CPU 预计算块（几何 + 深度）总量已逼近/超过 Swin 窗口上限，CPU 化是方向性错误
- 已回退（npu_patches.py/demo.py git checkout），baseline 0.54s 保持
- **后续（2026-09-30）**：✅ 该问题已由 O12 解决——留在 NPU 上消 gather/NonZero/
  同步（bit-exact），不新增 CPU 负载，E2E -31ms

#### 3.3.7 Swin-T 深挖（2026-09-30）：成本地图勘误 + FA 路线尸检 + shift 路径优化（O11 落地）

**背景**：img_backbone（Swin-T，**勘误：本模型是 Swin-Tiny 非 Swin-B**——swin_tiny
checkpoint，embed 96 / depths [2,2,6,2]=12 块 / 窗 7×7 / 全 stage head_dim=32；
一览表原 "Swin-B + SwiGLU" 均为笔误已改）是 E2E 最大头（~187ms），本轮做完整成本
地图并验证 npu_prompt_flash_attention（FA）融合窗口注意力路线。

**一、探针方法论勘误（重要）**：早期单端 sync 探针把排在前面的未执行算子链错误吸收进
计时窗口（曾把 attention core 记到 proj 头上）。修正为**两端都 sync** 后与独立微基准
交叉验证，得到可信成本地图（串行口径，~187ms）：

| 桶 | 耗时 | 明细 |
|---|---|---|
| attention core 算子链 | 75.7ms (39%) | stage0 11.1ms/块×2、stage1 ~7×2、stage2 ~4.2×6、stage3 ~2.3×2（q·scale 1.0 + q@kᵀ 5.0 + bias 0.74 + softmax 2.09 + @v 2.33 + 转置 1.34，stage0 逐算子定价） |
| FFN | 50.9ms | lin0 3.9 + GELU-erf 2.84 + lin1 3.9 + 残差（GEMM ~44ms 健康，q@kᵀ 仅 145-234 GFLOPS 是 batch 4680 小矩阵固有低效） |
| qkv+proj GEMM | 33.9ms | 健康（proj 1.8ms、随 N 线性） |
| partition/roll/mask | 23.4ms | roll 2.31 + reverse roll 2.31（×6 shift 块）+ pad 0.67×12 + partition/reverse 拷贝 + mask 链 1.48×6 |
| LN+残差 | ~11ms | |

**二、FA 路线尸检（结构性不可行，勿再试）**：FA 内核本身很快——B=128/heads=3/seq=49/
D=32 实测 **0.612ms**（vs stage0 手工链 11.1ms 的 1/18），D∈{32..128} 全域支持且开销
主导（B·H×4 工作量只慢 2.7 倍）。但 310P 三重约束使路线整体净亏：

1. **batch≤128 硬限**（tiling 限制，报错 "do not support batch size more than 128"）：
   stage0 1560 窗需 13 块分批
2. **仅 fp16**：FA-aug 全链 vs fp32 手工链 rel 误差 ~1.6e-3，超 ±1e-4 检测噪声地板
3. **无 pse_shift**（Atlas 推理系列不支持 bias 加性项），atten_mask 只收 bool/int8——
   相对位置 bias 只能走 **SVD 扩维代数**（B_h=U_h·W_hᵀ 精确分解，49×49 满秩，
   U/W 拼进 head_dim 32→96，FA 内积自动还原 bias，U/W 每层加载期预计算）

端到端实测（v 正确 pad 到同 D 的决定性测试）：**全 stage 净亏 7-34ms**——
stage0 18.5 vs 11.1、stage1 15.2 vs 4.9、stage2 20.8 vs 3.2、stage3 36.0 vs 2.4。
prep（strided cat + expand + fp32→fp16）+ 分块 + post 转置的拷贝开销远超内核收益。

- **踩坑记录**：早期 "hd=96 失败" 是**自己的 bug**——q/k 扩到 96 维但 v 还是 32 维
  （FA 要求三者同 D），报错被截断误导为 head_dim 白名单问题；D 扫描证明 32-128 全支持。
  教训：截断的错误信息会制造不存在的约束假设，先拿全量报错再下结论
- 数学侧证伪补充：softmax(s+B) 非线性不可拆分；"bias token" 追加方案不成立
  （额外 token 产生额外 softmax 项而非加性项）；atten_mask int8 若为加性语义也无法
  表达 fp bias（±127 量化）

**三、已证伪的其它 micro 路线**：SDPA 直调（"can not cast format when output is input"，
strided 输入）；kT contiguous 化（3.09 vs strided 5.45，但 contiguous 本身 2.44，净零）；
matmul 布局微优若干。attention core 75.7ms 在无融合算子前提下**已到硬件地板**
（Vector 全软 kernel 慢 35 倍见 §3.3.5，Cube 直调链路未通）。

**四、落地项（O11）**：mask 缓存 + pad/roll 四切片融合（bit-exact，-9ms E2E），
实现与验证细节见 §3.1 O11。**Swin 剩余最大杠杆**：FFN 融合 kernel
（`unum_ops/csrc/ascend/swin_ffn/`，并行会话搁置的 WIP，GELU 融合 + fp16 Cube GEMM，
理论 -20~30ms）；次优为 partition+reverse 与 pad/roll 的进一步合并（单次 gather 装配，
理论再 -6~8ms）。

#### 3.3.8 torchair 图模式复测勘误（2026-09-30）：不是"无收益"，是"不可用"

**两次历史结论均为接线 bug 下的 eager 空跑**：demo.py 计时循环直调
`model.test_step(...)`，而 `torch.compile` 只拦截 `__call__`/`forward`——`.test_step()`
经 `__getattr__` 穿透到未编译模块，torchair 路径根本不执行。09-18（1.1s 时代）与
09-30 首轮（"eager 484 / default 477 / full 509"）的"三模式同速"结论全部作废，
三组数字只是 eager 的波动。铁证：编译+首跑 0.5s"完成"（真 GE 编译需几十秒）、
fx_summary 无输出。

**有效测试**（修复接线后，npu:7）：eager 同调用路径 467-471ms / 48 dets；
torchair default 在 GE 转换阶段直接崩溃——`NotImplementedError:
torch.ops.aten.diagonal.default ge_converter is not implemented`（ERR03007，
崩在 metas 矩阵构建小图上，主计算图未轮到编译）；fullgraph=True 因 dynamo 断图
存在必然 Unsupported。dynamo 断图仅 2 处（npu_patches stash 禁区 +
bevfusion.py:264 上游 numpy 矩阵段），真正卡死在 torchair 的 aten→GE 转换器覆盖面。

**为什么图模式即使编过也吃不到"搬运+排队"的开销**：

1. **排队不是主要矛盾**：~4000 算子 × 20-50µs 发射 = 80-200ms host 时间，但发射是异步的、
   与设备执行重叠——设备侧真实执行 467ms 内核，host 每算子有 ~117µs 预算，宽裕藏在设备
   之下。证据：Swin 补丁删掉 11ms 设备时间，E2E 只回收 9ms（轻度 host-bound），设备执行
   才是关键路径；"小算子长尾 345ms + Cast/TransData 141ms"是 op_statistic 的**设备执行
   时间**，图模式不改变这些内核本身的速度
2. **搬运消不掉的根源是算子布局偏好**：TransData 风暴来自各 aclnn 算子对输入布局
   （NZ/ND 等）的不同要求，GE 图编译器在图内仍要插同样的布局转换；torchair 的融合
   覆盖面是逐元素/链式模式，不含本模型主导的 gather/scatter/sort/transpose 族——
   访存流量原样保留
3. **动态形状**：点数→体素数→bev_pool ranks 逐帧变化，图捕获在这些边界碎裂；能整图
   捕获的静态段（Swin/depthnet）恰是访存型小算子区，融合不动（fullgraph=True 遇断图
   直接 Unsupported）
4. **自定义 AscendC 算子不可入图**：bev_pool v1 / voxelize AscendC 是 op_extension，
   未做图兼容注册，图分区边界恰好切在管线中段
5. **fp32 契约**：有利可图的融合（matmul+逐元素、fp16 累加路径）多为 fp16 取向，fp32
   下编译器保持保守路径

**对"搬运/排队"有效的手段是手工融合算子**（改变算法与数据布局：bev_pool 399→23ms、
voxelize 72→25ms、FA 融合内核 0.61 vs 手工链 11.1ms）或全图 OM 级编译（动态形状硬骨头，
历史混合方案在 1.2s 时代有效、0.48s 时代无优势）。

**本轮代码修复**（防止第三次假阴性）：
- demo.py 新增 `run_step()`（test_step 逐语句等价：`data_preprocessor` +

#### 3.3.9 官方调度/OS 级优化项 A/B（2026-09-30 主测 + 10-08 诊断复测，全部无收益）

针对昇腾官方文档两组推荐项做了系统 A/B（TorchNPU《环境变量列表》+ ModelZoo《调度优化》）：
7 配置 × 2 轮交错 + 5 组诊断复测，npu:7 空载，README 标准命令 `--loop 5`，
基线为当日最新代码（O12 后 449ms median，48 dets / 0.819478 全程不变）。

**约束核查先行**（用户要求，310P 排除项）：

| 优化项 | 310P 判定 | 依据 |
|---|---|---|
| `TORCH_NPU_LAZY_FUSION`（DVM 算子融合） | ❌ 排除 | 官方支持型号仅 Atlas A2/A3 训练系列，推理系列不在列表 |
| `CPU_AFFINITY_CONF`（绑核） | ⚠️ 官方列表不含推理系列，**但实测在 310P 激活** | torch_npu 2.7.1 的 libtorch_npu.so 含实现；探针进程实测线程被钉核（26 线程→核 57、1 线程→核 58，非热点线程保持 0-63）——"支持列表"是验证范围不是硬 gating |
| `TASK_QUEUE_ENABLE` / `PER_STREAM_QUEUE` / `COMBINED_ENABLE` | ✅ | 支持型号明确含"Atlas 推理系列产品" |
| tcmalloc / malloc 大页 / Python 3.11 | ✅ 环境就绪 | libtcmalloc.so.4 已装；glibc 2.38 + THP=madvise；本机 Python 3.11.15 |

**实测**（各 5 轮 median；基线 449，环境噪声 ±5-25ms，尾部另有 ±50ms 级漂移须交错对照）：

| 配置 | median | 判定 |
|---|---|---|
| baseline（TASK_QUEUE_ENABLE 默认 L1） | 449 | — |
| `TASK_QUEUE_ENABLE=2`（L2 二级流水） | 449 | 无收益 |
| `TASK_QUEUE_ENABLE=0`（队列关闭，诊断） | 451 | L0≈L1≈L2，队列优化与本项目无关 |
| `TASK_QUEUE_ENABLE=2 + PER_STREAM_QUEUE=1` | 453-455 | 轻微负向（-4ms 级，实验性功能） |
| `COMBINED_ENABLE=1` | 451 | 无收益 |
| `CPU_AFFINITY_CONF=2`（细粒度绑核） | 449 | 激活但无收益（单进程空载场景） |
| `LD_PRELOAD=libtcmalloc.so.4` | 449 | 无收益（一次 490ms 为环境噪声，复测 449-450） |
| `GLIBC_TUNABLES=glibc.malloc.hugetlb=1` | 450 | 无收益（首轮 608ms 为大页 first-touch，warmup 可吸收） |

**结论**：
1. 单进程空载 demo 上调度/OS 级旋钮**零收益**——独立复证 §3.3.8 的"设备执行是关键路径"：
   ~4000 算子的下发藏在天花板下，host 侧再怎么优化流水/绑核/内存分配都拿不回时间
2. 官方文档的 host-bound 场景假设（"TASK_QUEUE_ENABLE 用于 host-bound 严重的网络"）
   与本项目画像不符；勿再重复投入
3. **唯一未测场景**：8 进程全量评测（性能.md §2：8 卡并发时单帧 1.9-2.5s vs 独占 1.3-1.6s，
   CPU 争用真实存在）——彼时 `CPU_AFFINITY_CONF`（310P 已证激活）+ tcmalloc 可能有效，
   属 40min 级实验，未列入本轮

### 4.4 核心发现

#### F1（P0）：bev_pool 分发到了 scatter_add 后端 —— 1.32s/帧

`bevfusion/ops/__init__.py` 的 `auto` 分发在 CUDA ext 不可用时直接把 `bev_pool` 换成
`bev_pool_torch`（scatter_add 版），**绕过了 `bev_pool()` 内部"默认 QuickCumsum"的意图**：

```python
try:
    from .bev_pool import bev_pool_ext
    if bev_pool_ext is None:
        bev_pool = bev_pool_torch        # ← NPU 上实际走这里
except ImportError:
    bev_pool = bev_pool_torch
```

scatter_add 版把 index 展开成 (N,80) int64（117MB）+ src (N,80)（587MB）做 AICPU 逐点累加，
单次 1.32s。QuickCumsum 版（kept bug 已修复，含排序/gather/cumsum 全链路）微基准 **0.225s，
且对 CPU fp32 参考值 max_abs=1.3e-3（fp32 重排级误差，与官方 CUDA 实现同 class）**。

#### F2（用户观察确认）：AICPU 算子占 65.9%

| 算子 | 次数 | 总耗时 | 单次最大 | 来源 |
|---|---|---|---|---|
| ScatterElements | 4 | 2668ms | 1323ms | bev_pool ×2 + dense() ×2（11.9ms） |
| NonZero | 90 | 122ms | 19ms | frustum kept 布尔掩码 + spconv/head 小 mask |
| Sort | 2 | 77ms | 38.8ms | voxelization int64 argsort（float32 会 >2^24 丢精度，保留 int64） |
| UniqueWithCountsExt2 | 4 | 51ms | 21.4ms | SparseConv3d 输出坐标 unique(dim=0) |
| IndexPut | 23 | 21ms | 10ms | spconv `_lookup_grid` |
| Cast | 88 | 20ms | 2.1ms | 零散 dtype 转换（int64 整数链） |
| UniqueConsecutive | 2 | 10.5ms | 5.7ms | voxelization |
| FloorDiv/Max/… | ~40 | ~18ms | — | _downsample_coords/voxelization 整数运算 |

结论：AICPU 大头是 ScatterElements（F1 修掉后 AICPU 占比从 66% → ~10%）。
剩余 NonZero/Sort/Unique 属"语义上必须的动态形状算子"，单次都在 20ms 级，优先级低。

#### F3：warmup 的 17 次遗留 aclop JIT 编译 ≈4s（一次性）

msprof host 事件显示 17 次 `AscendCL@aclopCompileAndExecute`（~290ms/次，含 952ms/531ms 两次大项），
全部落在 warmup 区段（+1.1 ~ +9.5s），推理前向零编译。这是 torch_npu 对无 aclnn 实现的算子
走遗留 aclop 编译路径的代价——**每进程一次**，demo 场景可接受；服务化部署若频繁拉起进程需要
关注（可用 ASCEND_CACHE_PATH 缓解；原建议"改走 torchair 整图编译规避"已勘误为
不可用，见 §3.3.8）。

#### F4：小算子风暴 —— host 分发是隐性天花板

推理前向 2758 个算子、平均 0.78ms，其中 Cast 880 / TransData 996 / Transpose 412 次。
修复 F1 后前向 ≈1.1s、device busy 可能降到 ~0.8s，此时 host launch 开销（~50-100µs/算子 × ~2700）
将与 device 时间同级，成为下一瓶颈。对策（**勘误 2026-09-30**）：原以为"torchair
整图编译"可吸收——实测不可用，GE 转换器缺 aten.diagonal 等（§3.3.8）；且 09-18
"三模式同速"本身是 test_step 穿透接线 bug 下的 eager 空跑。`--compile {off,full,default}`
参数已修复接线（demo.py `run_step`），default 现在响亮报 NotImplementedError。

#### F5：计算内核已经很快，无需算子级深度优化

Swin 主干 144ms、spconv 27ms、BEV 卷积 22ms。F1 修复后若要冲 100ms/帧目标（记忆 #32，
2026-09-24 由 40ms 改标），主战场是 ①frustum mask/gather 202ms、②小算子风暴、③host 分发——
不是 GEMM/Conv。
